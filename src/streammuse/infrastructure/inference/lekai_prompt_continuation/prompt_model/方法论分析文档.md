# 双轨钢琴无条件生成系统：方法论

## 一、任务定义

无条件生成双轨钢琴音乐（旋律+伴奏），模型自回归生成完整序列。

核心建模：
$$P(X) = \prod_{t=1}^{T} P(x_t | x_{<t})$$

---

## 二、序列格式（Beat-Marker）

### 2.1 格式定义

```
[BOS][TS][BPM] [BAR][BEAT][TRK_MEL][mel₀...][TRK_ACC][acc₀...] [BEAT][TRK_MEL][mel₁...][TRK_ACC][acc₁...] ... [BAR]... [EOS]
```

每一拍的结构：`[BEAT] [TRK_MEL] [mel patch tokens] [TRK_ACC] [acc patch tokens]`

### 2.2 设计要点

| 设计 | 说明 |
|------|------|
| **mel 先于 acc** | 旋律在前，伴奏在后，符合音乐创作直觉 |
| **track_marker 起始** | TRK_MEL(171) 标记 mel 开始，TRK_ACC(170) 标记 acc 开始 |
| **beat_marker 分隔** | 显式拍边界，模型"知道"每拍起点 |
| **bar 分隔** | 每小节开头一个 `bar_token`(255) |
| **固定音高顺序展开** | 不再插入 pitch token，88 个音高位按固定顺序依次展开 |
| **空 token 占位** | 没有音符的音高位也保留一个 token，占位形成退化 pianoroll patch 序列 |

### 2.3 Token 词表

| ID 范围 | 含义 |
|---------|------|
| 0-80 | patch 三进制编码（$3^4=81$ 种） |
| 81 | empty_patch_marker（空 patch 占位） |
| 170 | track_marker_acc（acc 轨起始） |
| 171 | track_marker_mel（mel 轨起始） |
| 172 | beat_marker |
| 255 | bar_token |
| 256/257/258 | EOS/BOS/PAD |
| 259-263 | 拍号（5 种） |
| 264-267 | BPM 分桶（4 种） |

vocab_size = 268

### 2.4 无条件 Loss

```
Input:  [BOS][TS][BPM] [BAR][BEAT][TRK_MEL][mel₀...][TRK_ACC][acc₀...] ... [EOS]
Labels: [BOS][TS][BPM] [BAR][BEAT][TRK_MEL][mel₀...][TRK_ACC][acc₀...] ... [EOS]
```

所有 token 参与 loss（标准语言模型训练）。

$$\mathcal{L} = -\frac{1}{T} \sum_{t=1}^{T} \log P_\theta(x_t | x_{<t})$$

## 三、编码：三进制 Patch + 固定音高展开

### 3.1 Patch 编码

将 (sustain, onset) 双通道 piano roll 的 $1 \times 4$ 时间窗口编码为单个 token：

$$\text{token} = \sum_{i=0}^{3} v_i \cdot 3^{3-i}, \quad v_i \in \{0, 1, 2\}$$

- 0 = 静音，1 = 延音（sustain only），2 = 起音（sustain + onset）

### 3.2 固定音高顺序展开

对每一拍、每一轨，不再只保留非零位置，而是沿 88 个音高按固定顺序依次输出 patch token：

```
原始 patch 序列: [p0, p1, p2, p3, ..., p87]
序列化结果:      [TRK_MEL, t0, t1, t2, t3, ..., t87]
```

其中：

- 若第 i 个音高位存在有效 patch，则 `ti` 为对应三进制 patch token
- 若第 i 个音高位全静音，则 `ti = EMPTY`

也就是说，模型不再显式预测“这是哪个 pitch”，而是默认第 1 个 token 对应最低音高位，第 88 个 token 对应最高音高位。这本质上是对 pianoroll 做固定顺序 patch 化后的退化编码。

这样做会牺牲稀疏压缩率，但换来更基础、更直接的表示方式：编码和解码都不依赖额外的位置 token。

## 四、训练与推理

### 4.1 模型架构

LLaMA 因果语言模型（768d, 18层, 6头, SwiGLU, RoPE）。因果注意力保证训练推理一致。

### 4.2 训练

- 数据增强：70% 概率音高平移 $\Delta \in [-5, 5]$
- Bucket batch sampler：按序列长度分桶减少 padding 开销
- 有效 batch = 2 × 127 = 254，AdamW, lr=5e-5, fp16

### 4.3 推理（无条件自回归）

```
初始化: [BOS, TS, BPM]

自回归生成直到 EOS 或达到最大长度
  模型逐 token 生成: BAR, BEAT, TRK_MEL, mel内容, TRK_ACC, acc内容 ...

解析生成序列 → 提取 mel_beats / acc_beats → MIDI
```

采样：temperature + top-k + top-p + repetition penalty。

## 五、为什么这样设计

### 5.1 为什么 mel 先于 acc

- 符合音乐创作直觉：先有旋律，再配伴奏
- 模型在同一拍内先生成旋律，再基于旋律上下文生成伴奏

### 5.2 为什么去掉 pitch token

| 编码 | 优劣 |
|------|------|
| 稀疏位置编码 | 序列更短，但需要显式位置 token，编解码逻辑更复杂 |
| **固定音高展开** | 序列更长，但结构最直接，天然对应 pianoroll patch 序列 |

去掉 pitch token 后：

- 模型学习目标更单纯，只需要在固定槽位预测 patch 内容
- 解码过程无需恢复位置索引，按槽位直接还原回 pianoroll
- 表示形式更接近图像 patch / 像素序列，是一个更基础的 baseline

### 5.3 为什么轨道标记在前

- 模型在生成内容前先"声明"轨道类型，提供更好的上下文信号
- 解析时可用 TRK 标记作为分段起始符，边界更清晰

### 5.4 为什么选拍级粒度

| 粒度 | 优劣 |
|------|------|
| 音符级 | 序列过长 |
| 拍级 | 符合音乐节奏结构，长度适中 |
| 小节级 | 粒度过粗 |

---

## 六、局限性

1. 仅支持钢琴双轨
2. 由于取消稀疏压缩，序列长度会明显增加
3. 无条件生成缺乏可控性
