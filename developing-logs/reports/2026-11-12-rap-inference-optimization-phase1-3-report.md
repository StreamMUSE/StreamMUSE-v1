## 2. 做了什么

共 30 个文件，其中源码 11 个（新增约 1200 行）。

### 2.1 第 1 阶段：Cyclic 回合之间保持连接

改动前，每个回合在用户敲完节奏之后才做三件事，全部算进 WAIT：查服务器能力、建 WebSocket、新建取音频的 HTTP 连接。

- **能力只查一次。** 缓存在后端里，会话出错时清掉。
- **取音频的客户端共用一个。** 整个后端一个，关闭后端时才关。
- **WebSocket 提前握手。** `LyricStreamConnection` 新增 `connect(session_id)`，只握手、不发 `start`；`open()` 发现已有同一个会话的握手就只发 `start`。
- **进入 USER 阶段时预热。** `InferenceService` 调后端的 `prepare()`，后端在后台并行查能力、预热两条取音频的连接、建一条备用的 WebSocket。`prepare()` 只入队，不在音频回调里做网络操作。
- **回退。** 备用连接超过 30 s 不用；发 `start` 失败就关掉它、按原来的方式建连。会话出错后三样都丢弃，下一个请求从头建连。
- **两边的 keep-alive。** httpx 和 uvicorn 默认都是 5 s 就关掉空闲连接，而回合间隔在 10 s 以上。新页面的客户端调到 60 s；render server 新增 `--http-keep-alive-seconds`，默认 75。

### 2.2 第 2 阶段：续写跨过请求边界

改动前，每个新会话的第一个 bar 前面没有本会话的 bar，所以不续写。这可能是 Andrew 听到“两段之间声音变了”的原因，还没验证。

- **协议：** 新增可选能力 `continuation_handoff_v1`。`start` 可以带 `continue_from: {"lyric_id": …}`。带了字段但没声明能力，服务器拒绝。
- **服务器：** 会话只在渲染第一个 bar 时把这个 ID 传给渲染器。渲染器在所有会话共用的缓存里查，命中就续写，没命中就单独合成，并在 `diagnostics.continuation` 里写明（`handoff: true` 或 `handoff_not_cached`）。
- **客户端：** 记下每个已交付 bar 的服务器歌词 ID。开新会话时找紧挨在前面的那一句，查到且服务器声明了能力才带 `continue_from`；否则 `start` 和以前一字不差。
- **可观测：** 每个 bar 的 `stage_timings` 事件附上服务器返回的续写信息，导出的 trace 里能直接数续写比例。
- **旧页面：** 它声明的能力列表保持原来的 4 个，不带 `continue_from`。

### 2.3 第 3 阶段：Steering 的长会话适配器

新模块 `infrastructure/rap/inference_steering.py`。用 `--inference-steering-adapter session` 启用，默认是 `bounded`（原来的行为）。

- **一次播放一个会话。** 第一个请求开会话，Stop 后 0.5 s 关闭，再次 Start 开新的。
- **延长请求：** 不开新会话，只向服务器报播放头。
- **改主题或 flow：** 发一条 `update`，服务器重写从新请求第一个 bar 起的所有 bar。
- **交付：** 服务器产出的每个 bar 取一次、准备一次，交给覆盖它的那个请求。提前渲染出来但还没有请求覆盖的 bar 先留着，请求一到立刻交付。
- **播放头怎么报（交接文档的方案 A）：** 后端看不到逐 bar 的播放位置，只能在请求到达时推算。开始和改主题的请求报“起始 bar − 1”，这是准确的；延长请求 `[s, s+m)` 报 `s − m//2 − 1`，会落后于实际位置但不会超前。因为会落后，提前量是歌词 4 个 bar、音频 3 个 bar。
- **出错：** 会话级的错误（断线、协议错误、请求超时）让当前请求报错并丢弃会话，下一个请求从它自己的第一个 bar 重开。

`InferenceService` 和页面没有因为第 3 阶段改动。

## 4. 需要注意的地方

### 4.1 和计划、交接文档的出入

| 阶段 | 原来写的 | 实际做的 | 原因 |
|---|---|---|---|
| 1 | 用户没敲出节奏时，提前建好的连接直接关掉 | 留给下一回合，靠年龄上限淘汰 | 只握手没 `start` 的连接不占服务器的会话名额 |
| 1 | 没提 keep-alive | 客户端 60 s，服务器默认 75 s | 不调的话连接在回合之间就被关了，复用不生效 |
| 2 | 用 `history[-1]` 的文本查上一句的 ID | 先按位置查，再按文本查 | Steering 的后续请求发出时，它前面那个 bar 已交付但还没播，`history[-1]` 是更早的一句 |
| 3 | 歌词提前 3、音频提前 2，和 v1.0 一样 | 4 和 3 | 推算的播放头会落后 |
| 3 | 先报播放头，再发 `update` | 先发 `update`，再报播放头 | 模拟里发现原来的顺序会让服务器先渲染一个马上作废的 bar，后半的修改因此晚一个 bar |
| 3 | 服务器返回的旧版本音频对应 stale | 没用服务器的 `older_version` | 旧版本的 bar 在改主题之前已经在页面缓冲里 |

交接文档里还有两处和实际不符：它说自己还没提交，其实已经在 `c90d0d8e` 里；它说这台机器上没有基线 trace，其实有。

### 4.2 一个改到了共用行为的地方

render server 的 keep-alive 默认值从 5 s 变成 75 s，对所有客户端生效，包括旧页面。旧页面的客户端仍然 5 s 就丢弃空闲连接，所以它的行为不变。要恢复原值，启动时加 `--http-keep-alive-seconds 5`。

### 4.3 发现但没有改的问题

**`InferenceService.steer()` 在某些 BPM 下会把目标 bar 多推后一个。** 它用“帧换算回 tick 再向上取整”找下一个 bar 边界；边界的帧数被四舍五入进位时，换算回来的 tick 比边界大一点，就跳到了再下一个 bar。

- 48 kHz 下 60、90、120 这类 BPM 的 bar 边界是整数帧，不受影响。
- 70 和 110 BPM 下，我用真实的服务层各试了 8 个位置，都是 4 个被推后。
- 两种适配器都受影响；验收用的 60 和 90 BPM 不受影响。
- 修法是按帧找边界，一两行。计划写了不动服务层，所以没改。

### 4.4 新适配器的已知弱点

- 发 `update` 或报播放头时连接刚好断开，会直接判会话失败，由下一个请求重开，这次修改会晚几秒。没有做“等自动重连后重发”，因为重发的 `update` 可能已经被服务器收到过一次。
- 播放头的推算依赖服务层“剩余不到一半时延长”这条规则。服务层改了这条规则，这里要跟着改。

### 4.5 模拟的局限

- 写词和合成是固定时间，没有重试、没有补救 wave、没有 GPU 上别的任务的干扰。
- 音频包是未压缩的 PCM，在本机传输，没有 Opus 编码和真实的传输时间。
- 延迟是固定的 250 ms，真实隧道 11-11 测到的 ping 在 225 到 493 ms 之间波动。
- 声音是合成的短音，听不出任何音色问题。第 2 阶段是否解决了声音不一致，模拟完全说明不了。

### 4.6 环境

- 这台 Mac 上 Homebrew 的 node 是坏的（缺 `libsimdjson.33.dylib`，10 月 9 日 simdjson 升级之后）。直接跑全量测试会多出 87 个调用 node 的失败。我用 `PATH="/usr/local/bin:$PATH"` 让测试用另一份 node v18，没有改动系统。
- 11-11 为测基线启动的 Mac 客户端（PID 61266，端口 8018）还在运行，隧道已断，我没有动它。
