## 4. 需要注意的地方

### 4.1 新一代 Qwen 在 vLLM 里比预想的慢

- Qwen3.5 以后是混合注意力模型（Gated DeltaNet）。vLLM 0.24 里，同一个请求的 32 条候选不会共享提示词的计算：前缀缓存命中率是 0，打开 `--enable-prefix-caching --mamba-cache-mode all` 也一样。所以 27B 写一行约 0.9 s，35B-A3B 也不比 9B 快。
- 显存给少了还会卡死：第一次用 `--gpu-memory-utilization 0.4` 和 4096 的上下文长度时，KV 缓存只够约 14 个请求，32 条候选挤满之后引擎不再前进。后来改成 0.75 和 2048，就没再出现。v1.1 的 9B 用的是 0.22。
- 想让大模型变快，可以试：把候选数从 32 降到 16；换 SGLang（它的前缀缓存可能对混合模型有效）；或者等 vLLM 支持。

### 4.2 发现了一个控制器的健壮性问题（已修，0cde79df）

- 歌词太晚到达时，到了提交时刻，服务器的声音和 eSpeak 都没准备好，会报 `no audio of any kind was ready at commit`；连续出现几次，会话就停了。这次只在 Qwen3.8 放 GPU 2、歌词严重迟到时触发。
- **原因有两个：** 一是现场编辑换到新主题后，本地兜底歌词按（主题，模板）查不到，抛出的异常被线程池吞了，本地兜底从此全空；二是提交失败时播放头不前进，服务器的歌词窗口、客户端的抓取和播放全都卡在那个 bar。
- **修法：** 兜底查不到时先用同模板的其他主题，再用音节数相同的任意一行（`line_for_any`）；本地兜底失败会报错误事件，不再静默；什么都没准备好时提交一个静音 bar，播放头照常前进，服务器把它记成没有上一句。
- **验证：** H200 上 Qwen2.5 + MOSS-Local，120 BPM 24 bar，在第 8 和 14 bar 编辑到新主题、新模板：没有错误，每个 bar 都有本地兜底。播放的声音：最新 14、旧版本 3、eSpeak 7。eSpeak 都紧跟在两次编辑之后（第 10–11、15–19 bar），因为编辑后要重写歌词再合成；而且这次 GPU 1 上有别人的 vLLM 和 MOSS 同时在跑。这个修复保证会话不断，不保证不退回。

### 4.3 续写补丁移植到 0.1.8

- **补丁：** `patches/sglang-omni-0.1.8-moss-local-continuation.patch`，用法写在 `patches/README.md`。
- **和 v1.5 的不同：** Local 版的输出不带前缀，所以补丁在合成阶段把前缀的 code 拼回去，让声码器和 v1.5 一样连着前缀一起解码。
- **踩过的坑：** 前缀 code 用完必须清空。第一次没清，前缀 code 被一路带到了声码器阶段，声码器回传结果时序列化失败，进程退出。
- **请求接口：** 和 0.1.4 的补丁一样（`prefix_audio` 和 `prefix_text`）。客户端仍会检查返回的开头确实是前缀，再把它切掉。

### 4.4 部署相关

- v1.1 的 render server 要加两个参数：`--vllm-extra-payload '{"chat_template_kwargs": {"enable_thinking": false}}'` 和 `--moss-sglang-resample-output`。完整命令见 `scripts/model_upgrade_stack.sh`。
- SGLang-Omni 0.1.8 的 MOSS-Local 默认会占 67% 的显存，同卡部署时要加 `--tts_engine.gpu_memory_fraction 0.3 --tts_engine.engine.mem_fraction_static 0.3`。
- Higgs 第一次启动要做 torch.compile 的内核调优，在忙碌的卡上超过了默认 600 s 的就绪时限。启动脚本已把时限放宽到 2400 s。

### 4.5 测量的局限

- **GPU 2 一直被别人占用：** TTS 的质量测试有一部分在 GPU 2 上跑，但延迟都在 GPU 1 上重测过。GPU 1 上另有你的 Qwen3-8B 服务，它全程空闲。
- **样本量小：** 每个 TTS 40 对，每种在线组合 1 段 90 BPM 加 1 段 120 BPM，一次性的偏差（比如 v1.1 那 5.6 s 的开场等待）分不出来。
- **服务配置不一样：** 其他 TTS 用的是 SGLang-Omni 0.1.8 的默认配置，没有像 MOSS 那样调过。IndexTTS 用的是不带任何服务优化的 Python 推理，它的 vLLM 部署方式没有试。

### 4.6 过程中的一个失误

- 停一批任务时，我用了按名字找进程的 `pkill -f`，结果匹配到了这条 ssh 命令自己的 shell，把连接断开了。这违反了“只按记录的 PID 停进程”的约定。
- 没有误杀别人的进程：之后我按 PID 核对过，只有我自己的批处理和 vLLM。后面全部改回按记录的进程组停止。
