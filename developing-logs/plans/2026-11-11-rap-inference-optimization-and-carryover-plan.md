## 背景

### 现在的系统

- 服务器：协议 v3 的歌词流，Qwen 逐 bar 写词，MOSS 逐 bar 合成并续写上一个 bar，对应 tag `rap-v1.0` 和 `rap-v1.1`。
- Mac 端：Andrew 在 10-21 到 11-11 之间加了新页面 `/inference`，有两个模式。
  - **Cyclic exchange：** 用户敲一小节节奏，模型按这个节奏回应两小节，循环进行。用户敲完到模型开始出声之间的等待叫 WAIT。
  - **Continuous steering：** 模型一直 rap，用户随时改主题或 flow。
- 新页面把 v3 当成一次性请求来用：每个请求新开一个会话，用完就关。说明见 [inference-optimization-handoff](../../docs/developer-guide/inference-optimization-handoff.md)。

### 2026-11-11 的基线

配置：H200 上 Qwen2.5-7B（GPU 1）加 MOSS-TTS-Local v1.5 续写（GPU 2），32 条候选，Opus；Mac 端 60 BPM，USER 1 个 bar、MODEL 2 个 bar，WAV 输出（不出声），经 SSH 隧道。5 个回合全部完成，没有缺失。

| 从发出请求起（5 个回合的中位数） | 耗时 | 占 WAIT |
|---|---:|---:|
| 到 Mac 收到 bar 0 的歌词 | 2577 ms | 60% |
| 再到 bar 0 的音频在 Mac 上准备好 | 1382 ms | 32% |
| 其中：取音频的请求 | 1302 ms | |
| 其中：服务器合成加对齐（含 MOSS 439 ms） | 471 ms | |
| 其中：Mac 解码、拉伸、混音 | 78 ms | |
| 准备好到 MODEL 开始 | 6 ms | |
| **WAIT 合计** | **4262 ms**（最小 3760，最大 4488） | |

同一条隧道上单独测的往返（各 5 次）：

| | 中位数 |
|---|---:|
| 查服务器能力的 GET，每次新建连接 | 1047 ms |
| WebSocket 握手，每次新建连接 | 1069 ms |
| 同一个 GET，复用已有连接 | 507 ms |

**结论：**

- 收到第一句歌词之前的 2.58 s 里，查能力和建 WebSocket 两步就占约 2.1 s；服务器写一句词只要 0.1 到 0.2 s（bar 1 的歌词比 bar 0 晚 120 到 180 ms 到）。
- 每新建一条连接比复用连接多花约 0.55 s。一个请求现在要新建 3 条：查能力、WebSocket、取音频。
- 服务器真正在算的时间（写词加合成）约 0.6 s，只占 WAIT 的 15%。

Andrew 11-11 在他的机器上测的 WAIT 中位数是 5.34 s（5 个回合）。网络不同，不能直接和上表比，但结构应该一样。Steering 模式他测过 1 次：改主题和 flow 后 7.48 s 才播到新版本；我们这边还没测。

### 已知问题

- **声音不一致：** Andrew 听到两段之间 rapper 的声音完全变了。代码上，新会话的第一个 bar 没有上一个 bar 的音频可接，所以不续写；这是否就是原因还没验证。
- **bar 数上限不一致：** 适配器声明单个请求最多 64 个 bar，服务器的有界会话只接受 1 到 8 个。
- **取消只在客户端生效：** 没有确认 GPU 上的生成真的停了。

## 目标

1. Cyclic 的 WAIT 从约 4.3 s 降到 2 s 以内，不增加缺失。
2. Steering 改主题后到新内容播出的时间，回到 v1.0 长会话的水平：赶得上就在下一个 bar，赶不上晚一个 bar。
3. 请求边界和回合边界上续写不断。
4. 把四份旧计划里积压的盲听一次听完，把积压的决定定下来。

- 不在这份计划里做新的交互功能（麦克风、双角色、filler、中文），那些在 Andrew 的[路线图](../../docs/research/2026-11-05-interaction-next-steps.md)里。

## 第 1 阶段：Cyclic 的回合之间保持连接

现在每个回合都在用户敲完之后才查能力、建 WebSocket、建取音频的连接，这三步都算进了 WAIT。改成查能力和取音频的连接在一次播放期间只建一次，WebSocket 的握手提前做完。

- 服务器能力只查一次，缓存到停止或出错为止。
- 取音频的 HTTP 客户端在回合之间复用。
- WebSocket 的握手挪到等待之外，两种做法，先试第一种：
  - **提前建连：** 在 USER 阶段就把下一回合的 WebSocket 建好，用户敲完再发 `start`。服务器不用改：它接受连接后会一直等 `start`，没有超时。客户端要把现在合在一起的“建连并发 `start`”拆成两步。
  - **一条连接开多个回合：** 现在一条连接只对应一个会话，收到 `stop` 就结束，所以这种做法要改服务器。提前建连不够时再考虑。
- 出错、Stop、Reset 时照常关闭并重建，旧回合的结果不能串进新回合。用户没敲出节奏时，提前建好的连接直接关掉。

**估算：** WAIT 降到约 1.6 s。算法是从 4.26 s 里去掉查能力（约 1.05 s）、WebSocket 握手（约 1.07 s）和取音频时新建连接多出的开销（约 0.55 s）。这是按今天的隧道往返算的，没有实测。

**验收：**

- 同样条件下 5 个回合的 WAIT 中位数低于 2 s，缺失仍为 0。
- 断线、Stop、Reset、连续两次 Start 的现有测试都通过；新增“回合之间连接复用”和“连接中途断开后重建”的测试。

## 第 2 阶段：续写跨过请求边界

- 开新回合或新请求时，带上上一句实际播出的歌词 ID；服务器用它在渲染器的前缀缓存里找上一个 bar 的音频。缓存是所有会话共用的，保留最近 64 条。
- 找不到就不续写，和现在一样，并在 `diagnostics.continuation` 里写明原因。

**验收：**

- 除了整场的第一个 bar，其余 bar 的续写比例达到 95% 以上（v1.0 长会话是 99%）。
- 用 10-12 的方法算相邻 bar 的说话人相似度，回合边界处不低于回合内部。
- 请 Andrew 再听一次，确认声音变化的问题是否消失。

## 第 3 阶段：Steering 改用长会话

写一个新的适配器，只给 steering 模式用：

- 一次播放期间只开一个会话，歌词提前 3 个 bar、音频提前 2 个 bar，和 v1.0 一样。
- 页面要求“延长范围”时，翻译成向服务器回报播放头。
- 输入版本变了（改了主题或 flow），翻译成一条 `update`，由服务器重写还没提交的 bar。
- 服务器返回的旧版本音频对应页面上的 stale，照现有规则计时和标记。
- `InferenceService`、页面和旧模式都不改。

**验收：**

- 第 0 阶段同样的 12 次修改：在 bar 前半修改的，新内容在下一个 bar 播出；后半修改的，最多晚一个 bar。缺失为 0。
- 续写比例 95% 以上。
- 现有 steering 测试全部通过。

**2026-11-11：第 1 阶段（代码和单元测试完成，真实验收未做）**

提交：`feat(rap): keep inference transports between cyclic turns`（提交号见本节末尾的汇总表）。H200 当天连不上，下面“验收”一栏的两项都没有做。

做了什么：

- `LyricStreamConnection` 新增 `connect(session_id)`，只做 WebSocket 握手、不发 `start`；`open()` 发现已有同一个会话的握手就只发 `start`。发送失败（握手已失效）时关掉它，按原来的方式重新建连并发 `start`。没有调用过 `connect()` 时 `open()` 的行为和以前一样。
- `HttpBarAudioSource` 新增可选参数 `keepalive_expiry_seconds` 和方法 `warm(n)`（并发发 n 个便宜的 GET，把连接池里的连接建好或刷新）。不传参数时和以前一样用 httpx 默认的 5 s，旧页面不受影响；新页面通过 `RapAudioFactories.create_inference_bar_audio_source` 用 60 s。
- `RealInferenceBackend`：服务器能力只查一次；取音频的 source 整个后端共用一个；新增 `prepare()`（只入队，后台并行做三件事：查能力、预热两条取音频的连接、建一条握手完成但未发 `start` 的 WebSocket）。请求到来时优先用这条备用连接，超过 30 s 或发送失败就关掉、按原方式建连。会话出错时三样都丢弃，下一个请求从头建连。
- `InferenceService._begin_user()` 在每次进入 USER 阶段时调用后端的 `prepare()`（后端没有这个方法就跳过）。只影响 cyclic 模式。
- render server 新增 `--http-keep-alive-seconds`，默认 75（uvicorn 自己的默认是 5）。

测试：

- 新增 28 个测试，全量 3428 通过、5 跳过、5 失败（5 个失败是已知的 FastPitch/timing 缺语料，和基线一样）。
- 新增真实套接字的集成测试 `tests/integration/test_inference_live_transport.py`：线程里起 uvicorn，挂 v3 路由，配假的写词和合成，用真的 `LyricStreamConnection`、`HttpBarAudioSource` 和 `RealInferenceBackend` 连。验证了：`prepare()` 之后服务器上有一条握手完成但没有会话的 WebSocket；请求发出到两个 bar 都交付的过程中，服务器没有收到任何新的 TCP 连接，也没有再查能力；之后的回合继续复用同一批 HTTP 连接；备用连接被掐断后自动重新建连，回合照常完成；服务器 keep-alive 很短时只是享受不到复用，回合不失败。
- 本机模拟（不是验收）：在客户端和测试服务器之间加一个 TCP 转发，每个方向延迟 250 ms，新建连接多等一次往返；假的合成固定睡 0.47 s，写词不计时。请求发出到第一个 bar 交付，不做 `prepare()` 时中位数 3643 ms，做了之后 1039 ms（各 5 次）。这只说明连接开销的变化，真实的 WAIT 还要加上写词、音频包传输和 Mac 端准备的时间。

和计划的出入：

- 计划写“用户没敲出节奏时，提前建好的连接直接关掉”。实际做法是留着给下一回合用：15 s 以内的备用连接不重建，超过 30 s 的不使用。服务器上一条只握手没 `start` 的连接不占会话名额。
- 计划没提两边的 keep-alive：httpx 默认 5 s 丢弃空闲连接，uvicorn 默认 5 s 关闭空闲连接，而回合间隔在 10 s 以上。所以客户端（仅新页面）调到 60 s，服务器默认调到 75 s。**服务器这一项对所有客户端生效**，包括旧页面；旧页面的客户端仍然 5 s 就丢弃空闲连接，所以行为不变。要恢复原值，启动时加 `--http-keep-alive-seconds 5`。
- 交接文档建议的“失败时由后端重试一次”做了两层：连接对象自己会用同一个会话 ID 重新握手；后端另外兜底，换一条新连接和新的会话 ID 再试一次。
- 这台 Mac 上 Homebrew 的 node 是坏的（缺 `libsimdjson.33.dylib`），直接跑全量测试会多出 87 个调用 node 的失败。测试时用 `PATH="/usr/local/bin:$PATH"` 让它用另一份 node v18，没有改动系统。
