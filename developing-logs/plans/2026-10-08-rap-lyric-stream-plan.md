# 歌词流、单小节 chunk 与实时交互：计划（2026-10-08，2026-10-12 修订）

> **2026-10-12 修订：音频改由服务器持续预生成，客户端按歌词 ID 取。**
>
> - 服务器持续写歌词，也持续往前合成音频，不用等客户端来要。
> - 客户端仍然按 bar 发请求，但请求里只是一个歌词 ID，意思是“把这句的音频给我”：
>   - 合成好了就直接返回；
>   - 没合成好，服务器就把它排到最前面优先合成。
> - 听众改了主题或 flow 以后，某个 bar 可能已经有旧版本的音频：
>   - 服务器先把旧版本发过去，同时优先合成新版本；
>   - 到播放的时候新版本还没好，客户端就播旧版本。
> - **Mac 暂缓（2026-10-08 决定）：** 这次只做 H200，Mac 暂时保留现在的 2-bar 路径。

## 目标

1. **歌词流：** 服务器按 bar 依次往后写歌词，每句都参考前面的句子来选：只要“后一句和前面接得上”，不再两句配对。写好就推送给客户端，两边各存一份歌词日志。
2. **音频流：** 服务器按 bar 持续往前合成音频，存起来；客户端按歌词 ID 来取。
3. **chunk 改成 1 个 bar：** 按 bar 合成、取、提交、兜底。
4. **兜底念同一份词：** eSpeak 兜底念歌词流里的词。只有某个 bar 的歌词到提交前都没收到（应该非常少），才用本地生成的歌词。
5. **实时交互：** 听众可以随时修改之后小节的**主题**和 **flow 模板**，系统尽快体现出来，并且永远不会因为改动而断音。
6. **先在 H200 上做好：** 每个 bar 32 条候选。有了足够的实验数据之后，再决定能不能减少。

## 架构

```text
                      ┌──────────────── 服务器（render server 进程，每个会话一套）────────────────┐
                      │                                                                          │
 客户端 ──WS 会话────►│  ① 写词循环：歌词领先播放头 K 个 bar                                       │
 （剧本、修改、提交回报）│     Qwen（vLLM，单独一张卡）n=32 → 硬门槛 → 按“接上前文”评分 → 歌词日志 │
       ◄──推送歌词────┤                                                                          │
                      │  ② 合成循环：音频领先播放头 A 个 bar                                       │
                      │     队列：每个 bar 最新版本的歌词，按 bar 号从小到大                       │
                      │     MOSS（SGLang-Omni）一行 → MMS → 打包 → [Opus] → 音频存储（按歌词 ID）  │
                      │                                                                          │
 客户端 ──取音频─────►│  ③ 取音频：GET …/bars/{bar}/audio?lyric_id=…&wait_ms=…                   │
   （按歌词 ID）        │     这一版已经合成好         → 直接返回                                  │
       ◄──音频包──────┤     没好，但有旧版本的音频   → 先返回旧版本，并把这一版排到最前面          │
                      │     什么都没有               → 排到最前面，等它合成好（最多等 wait_ms）   │
                      └──────────────────────────────────────────────────────────────────────────┘

客户端：
  收到歌词 → 存进日志 → 立刻渲染这句的 eSpeak 兜底
  bar k 进入取音频窗口 → 取最新版本的音频 → 收到后做 R3、混音
  （收到的是旧版本：先留着当后备，继续取新版本）
  提交 bar k（它开始前 1 tick），按这个顺序选：
    1. 最新版本的远端音频
    2. 旧版本的远端音频（听众刚改过时会用到）
    3. eSpeak 念最新版本的词
    4. 本地生成的歌词（很少）
  提交后回报 committed {bar, lyric_id, source}
```

### 为什么不需要专门的优先级调度

- **没人修改时：** 合成队列就是按 bar 号从小到大排的，队首永远是“最快要播的那个 bar”。服务器按顺序合成，正好就是最需要的。客户端来取的时候，音频通常早就合成好了，直接返回。
- **有人修改时，只多了两条规则：**
  - 被替代的旧版本，还没开始合成的就从队列里删掉；**已经在合成的让它做完**，做完的结果就是“旧版本的后备”；
  - 客户端来取某个还没合成好的版本时，把它挪到队首。因为新版本也是按 bar 号排的，挪到队首基本也就是它本来的位置。

### 歌词 ID 和版本

- 歌词 ID 由 bar 号和修订版本号，加上对文本、flow、音节时间表的哈希构成。同一个 bar 改一次主题，就多一个版本。
- **服务器端：** 音频存储和缓存都以歌词 ID 为键（再加上 MOSS 参数、续写前缀的 ID），所以不同版本的音频互不覆盖。
- **客户端：**
  - 用歌词 ID 判断收到的音频对应哪一版；
  - 每个 bar 记住“最新版本的歌词”和“已经拿到的各版本音频”；
  - 提交时按上面的顺序选。
- **取音频时，客户端也带上这句歌词的内容**（文本、flow、时间表，只有几百字节）。这样服务器重启、丢了歌词日志以后，也能照常合成；服务器会核对 ID 和内容是否一致。

### 位置和领先量（都以 bar 为单位）

- **播放头 P：** 最后一个已提交的 bar，来自客户端回报的 `committed`。P 及之前的 bar 都已冻结；**P 之后的每个 bar 都还可以改，直到它被提交为止。**
- **歌词领先 K：** 写词循环保证 P+1 到 P+K 都有最新版本的歌词，默认 K = 3。
- **音频领先 A：** 合成循环保证 P+1 到 P+A 都有最新版本的音频，默认 A = 2。要求 K ≥ A + 1，这样合成时总有歌词可用。
- **取音频窗口：** bar k 的最新版本歌词到达，并且 k ≤ P + 2，客户端就去取。请求最多等到这个 bar 的提交点。

## 时间预算（每个 bar 2.667 s；按 10-01 的实测推算，标“估算”）

- **合成一个 bar：** MOSS 一行约 0.51 s（约 34 帧加 31 步预热，约 67 步），加上 MMS、打包、Opus 约 0.1 s，合计约 **0.6 s**，估算。
- **稳态占用：** 每 2.667 s 合成一个 bar，MOSS 那张卡只用了约 23%。写词每个 bar 约 0.15 s（n=32，估算），在另一张卡上。
- **关键路径：** 音频提前 A = 2 个 bar 就已经合成好，所以客户端取音频时通常只剩网络开销：10-01 当天 VPN 下约 0.67 s，再加 Mac 端解码、R3、混音约 0.1 s，远小于 2.6 s 的预算。
- **修改后的反应时间：** 写词约 0.15 s，合成约 0.6 s，客户端取回约 0.67 s，合计约 **1.4 s**，估算。
  - 修改发生在当前 bar 结束前 1.4 s 以上：**下一个 bar** 就是新内容；
  - 否则从下下个 bar 开始。

  所以从修改到听见新内容约 1.4 到 4.1 s；现在用 2-bar chunk，最长约 10.7 s。

## 实时交互：主题和 flow 模板可以随时改

1. **剧本改成可修改的。** 现在的 `RapScenario` 是固定不变的预排表。改成一份“现行计划”，记录每个 bar 的主题和 flow 模板；每次修改都带一个递增的编辑序号。
2. **修改的流程：**
   - 客户端发送 `update {edit_seq, from_bar, topic?, flow_template?}`，从 max(from_bar, P+1) 开始生效。
   - 写词循环把这些 bar 的歌词标为“被替代”，从最早的那个 bar 开始按新的主题和 flow 重写，推送新版本。
   - 合成循环删掉旧版本里还没开始的任务，按 bar 号依次合成新版本。
3. **客户端：** 收到新版本，就重新渲染这个 bar 的 eSpeak 兜底，再去取新版本的音频。已经拿到的旧版本音频继续保留，作为后备。
4. **新版本来不及时：** 到了提交点，新版本的音频还没好，就**播旧版本的远端音频**（D3）。听众听到的是旧主题，但声音是完整的远端人声，修改从下一个 bar 开始体现。
5. **连续修改：** 短时间内改了好几次，以最后一次为准。中间版本还没开始合成的直接丢弃。
6. **改 flow 的影响：**
   - 新的 flow 决定这句要多少个音节、重音落在哪里，写词的硬门槛和评分跟着变。
   - eSpeak 兜底和 R3 的目标时间都来自歌词记录里的音节时间表，所以自动一致。
   - 鼓的节奏型不受影响。
7. **控制接口：** demo 服务新增 `POST /api/control/plan`，网页控制面板加主题和 flow 的输入框，界面可以先做最简单的版本。

## 选词：逐句往后

- 每个 bar 一批 32 条候选，参数可以配置。
- 硬门槛：音节数和 flow 的槽位数一致，不能重复已经用过的句子。
- 评分沿用现有的各项，并补上“接前文”：
  - 押韵锚点：取前面同一押韵组里那一句的尾韵，修掉现在 `rhyme_anchors={}` 的问题；
  - 和上一句的连贯性；
  - 主题、重音对齐、新鲜度。
- 合格的不足 3 条时补救一次，预计很少发生。
- 选出最高分的一条，写进歌词日志并推送，不再做配对。

## 第 0 阶段：先在 H200 上测两件事

**0a. 单句合成的效果和时间**

- 同一组 20 条语料，对比三种方式：
  - 现在：两句一次合成；
  - 单句独立合成，`token_count` 为 33；
  - 单句续写：接着上一句的音频说，离线用 HF remote code 来做。
- **指标：**
  - WER；
  - 相邻 bar 之间的说话人相似度；
  - 接缝处的音量和音高跳变；
  - MMS 测到的起点和目标的偏差；
  - 单句的 MOSS 耗时，要实测 delay 预热；
  - 盲听，需要你来听。

**0b. Mac 上的 GPU 预算**：暂缓，和第 8 阶段一起做。

**0c. 计时**

- 按 bar 记录：歌词到达、音频合成完成、客户端取回、提交，以及每一步距这个 bar 开始还有多久。
- 再加上：修改到生效的延迟、每个 bar 的版本数、播旧版本的次数。

## 第 1 阶段：逐句写词（先离线做）

1. 新增 `SequentialLyricWriter`（application 层），复用现有的这些部分：prompt 构造、生成器、`CmuProsodyAnalyzer`、评分和硬门槛。
   - 输入：前文、这个 bar 的主题和 flow、押韵锚点、seed。
   - 输出：一条歌词记录，包括文本、音节时间表、评分、候选 ledger 和来源信息。
2. prompt 新增“上一句”和“押韵要求”两部分，prompt 版本号加一。
3. 用固定剧本离线写 48 个 bar，对比现在的“两句独立写、事后配对”：
   - 押韵命中率；
   - 平均分；
   - 补救比例；
   - 选中句子的可懂度：用 MOSS 合成后测 WER。

**测试：**

- 用假生成器验证：选择结果是确定的。
- 押韵锚点取的是同一押韵组的前一句。
- 合格的不足 3 条时补救一次，补救后仍然不足时报错。

## 第 2 阶段：会话服务和写词循环

1. **render server 新增 WebSocket `/v1/rap/sessions/{session_id}`：**

   | 方向 | 消息 |
   |---|---|
   | 客户端 → 服务器 | `start {现行计划, tempo, start_bar, 已有的歌词历史}` |
   | 客户端 → 服务器 | `update {edit_seq, from_bar, topic?, flow_template?}` |
   | 客户端 → 服务器 | `committed {bar, lyric_id, source: remote_latest/remote_old/espeak/local_text, text?}` |
   | 客户端 → 服务器 | `stop`、`reset` |
   | 服务器 → 客户端 | `lyric {bar, revision, lyric_id, text, flow, schedule, scores, provenance}` |
   | 服务器 → 客户端 | `superseded {bars, edit_seq}` |
   | 服务器 → 客户端 | `audio_ready {bar, lyric_id}`（可选，用来提示客户端去取） |
   | 服务器 → 客户端 | `error` |

2. **写词循环：**
   - 每个会话一个，保证 P+1 到 P+K 都有最新版本的歌词。
   - 收到 `update` 就从 max(from_bar, P+1) 开始重写。
   - 收到 `committed` 就推进播放头 P，并把实际播出的那句作为前文。
3. **歌词的来源信息：** 写词模型和 revision、prompt 版本、采样参数、n、评分权重，记录在每条歌词记录的 `provenance` 里。
4. **断线和恢复：**
   - 客户端重连后发 `start`，带上自己的歌词日志。
   - 服务器重启后状态丢失，也靠客户端发来的日志恢复。
5. **部署：** vLLM 单独占一张卡，写词循环在 render server 进程里调用它。

**测试（用假生成器和假时钟）：**

- 领先上限；
- 修改和版本；
- `committed` 推进播放头；
- 重连恢复；
- 停止和重置时的清理；
- 协议消息的校验，包括越界和重复的 `edit_seq`。

## 第 3 阶段：合成循环、音频存储和取音频接口

1. **新的 domain 类型（协议 v3）：** `BarLyricRecord`、`BarAudioManifest`。
   - 音频身份 = 歌词 ID + MOSS 参数 + 续写前缀 ID（第 6 阶段才有）。
   - manifest 记录：对应的歌词 ID、source 起点、置信度和诊断。
2. **合成循环：**
   - 每个会话一个队列，内容是 P+1 到 P+A 这些 bar 的最新版本歌词，按 bar 号排序；一次只合成一个。
   - 流程是：MOSS 一行（`token_count` = 一个 bar 的帧数）、MMS、打包、Opus，然后存进音频存储。
   - 存储放在内存里，同时落盘缓存，沿用 v2 的产物存储和 producer 指纹的做法。
3. **取音频接口 `GET /v1/rap/sessions/{sid}/bars/{bar}/audio?lyric_id=…&wait_ms=…`：** 请求里同时带上歌词内容。

   | 情况 | 服务器怎么做 |
   |---|---|
   | 这一版已经合成好 | 立刻返回 |
   | 这一版没好，但这个 bar 有旧版本的音频 | 立刻返回旧版本（响应里标明“返回的是哪一版、请求的那一版还在合成”），同时把请求的版本挪到队首 |
   | 这个 bar 什么都没有 | 把请求的版本挪到队首，等它合成好，最多等 `wait_ms`；超时返回“尚未就绪” |

4. **把 2-bar 的硬编码改成可配置的 bar 数：** `TwoBarRenderRequest`、`chunk_render_request`、MOSS 适配器的时长计算、R3 的目标时间。1 个 bar 和 2 个 bar 都要有测试。
5. **客户端的 strategy：** 增加单 bar 的 v3 路径，R3、混音和校验都按单个 bar 来做。

**测试：**

- 合成的顺序；
- 被替代的版本：还没开始的被丢弃，已经在合成的会做完；
- 三种取音频的情况；
- 队首插队；
- 歌词 ID 和内容不一致时拒绝；
- 单 bar 的端到端：用假 MOSS 和假 MMS，走完打包、客户端校验和 R3；
- 用真实 rubberband 时，客户端输出和服务器端拉伸逐字节一致。

## 第 4 阶段：客户端控制器改成按 bar 运行

1. 新的控制器（替代 `RollingRapChunkController` 的 2-bar 逻辑）：
   - 订阅歌词流，维护本地的歌词日志；
   - 歌词一到，立刻在后台渲染 eSpeak 兜底；
   - 按取音频窗口去取最新版本的音频。收到的是旧版本，就先留着当后备，再取新版本；
   - 每个 bar 在开始前 1 tick 提交，按 D3 的顺序选，然后回报 `committed`。
2. **会话日志：** 按 bar 记录各版本歌词和音频的到达时间、最终用了哪一种来源，以及原因。
3. **`client_simulation`：** 改成按真实节奏、按 bar 驱动，并模拟会话通道和修改操作。

**测试：**

- 最新版本先到、只有旧版本、只有 eSpeak、连歌词都没有，这四种情况下的提交结果；
- 停止、重置、epoch 切换时，所有在途的请求和渲染都能被取消。

## 第 5 阶段：实时交互

1. 现行计划和编辑序号，按“实时交互”一节实现。
2. 会话通道的 `update`，加上 demo 服务的 `POST /api/control/plan`，以及网页控制面板的最简单版本。
3. **测试：**
   - 换主题、换 flow 之后，新内容从正确的 bar 开始生效；
   - 已提交的 bar 不受影响；
   - 新版本来不及时，播的是旧版本的远端音频；
   - 连续修改多次，以最后一次为准；
   - D7 的情况被记录下来。
4. **验收（H200）：** 真实会话中修改 10 次。
   - 反应时间：在当前 bar 结束前 1.5 s 以上发生的修改，下一个 bar 就要体现；
   - 修改前后没有断音，也没有 underrun；
   - 记录用 eSpeak 兜底的比例。

## 第 6 阶段：跨 bar 续写（按 0a 的结果决定做不做）

- 给 SGLang-Omni 打补丁：把前缀音频的 codes 作为 assistant 消息传进去，让 bar k 接着 bar k−1 的音频往下说。前缀音频存在服务器端，前缀缺失时退回到不续写。
- **和版本的关系：** bar k 总是接着 bar k−1 的**最新版本**来合成。如果 bar k−1 最后播的是旧版本，bar k 的接缝就不完全连贯。这只出现在修改之后，先接受，并记录发生的比例。
- **验收：** 相邻 bar 的说话人相似度和接缝指标都比单句独立合成好；WER 不变差；单句 MOSS 增加的时间不超过 100 ms；再加上盲听。

## 第 7 阶段：沿用的速度优化

打包只做一遍，Opus 编解码改成进程内（来自流水线重叠计划的第 4 阶段）。单 bar 之后请求数翻倍，每次请求的固定开销更值得省。

## 第 8 阶段：Mac 部署（暂缓，以后单独立项）

单 bar 的合成加上每个 bar 写一批候选，在 Mac 的单块 GPU 上很可能跟不上 2.667 s 的节奏：q8 的 MOSS 加每个 bar 16 条候选，估算约占 101%。到时候再测、再优化，比如 MOSS 用 q4、减少候选数，或者 Mac 保留 2-bar 的音频单位。

## 第 9 阶段：H200 整体复测

- **指标：**
  - 每个 bar 的音频提前多久合成好；
  - 客户端取回的耗时和余量；
  - 按 bar 的兜底率，以及歌词没到的比例（目标接近 0）；
  - underrun；
  - 修改的反应时间；
  - 播旧版本的比例；
  - 歌词质量：押韵命中率、评分、WER；
  - 两张卡的 GPU 占用。
- 更新 profiling 报告和 quickstart。

## 执行顺序

```text
第 0 阶段（H200 上测单句合成、补全计时）
  → 第 1 阶段（逐句写词，离线）
  → 第 2 阶段（会话服务、写词循环）
  → 第 3 阶段（合成循环、取音频接口）
  → 第 4 阶段（客户端控制器）
  → 第 5 阶段（实时交互）

  → 第 7 阶段
  → 第 9 阶段（H200 复测）

```

第 2 阶段和第 3 阶段的接口（歌词记录、歌词 ID）先定下来之后，两者可以并行开发。

## 风险

| 风险 | 应对 |
|---|---|
| 单句合成的接缝比两句一次合成差 | 0a 实测；第 6 阶段用续写补上 |
| 修改后服务器做了很多白用的合成 | A 只有 2 个 bar；旧版本没开始的就丢弃；已经合成的旧版本正好当后备 |
| 播旧版本时，听众听到的是旧主题 | 只影响修改之后的一两个 bar；D7 记录比例；反应时间约 1.4 到 4.1 s |
| 服务器和客户端的状态不一致：版本、播放头 | 歌词 ID 带版本号；客户端回报 `committed`；重连时用客户端的日志恢复 |
| 取音频时网络抖动 | 音频提前 A 个 bar 就合成好了，取音频窗口给了约 2.6 s 以上的预算；出问题还有旧版本和 eSpeak 两层兜底 |
| 改动面大：domain、协议、服务器、控制器都要动 | v2 全程保留，可以回滚；按阶段提交，每个阶段都有单测和真实会话验收 |
