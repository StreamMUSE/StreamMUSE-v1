# RAP chunk 准备流程的重叠与流水线优化：计划（2026-10-08）

> **2026-10-08 更新：本计划的一部分已被[歌词流计划](2026-10-08-rap-lyric-stream-plan.md)替代。**
>
> - **被替代：** 第 2 阶段（一次 20 条）和第 3 阶段（服务器端预取）。写词已经独立成为按 bar 往后写的歌词流，每个 bar 的候选数是 H200 32 条、Mac 16 条。
> - **第 1 阶段（兜底并行）：** 在新方案里自然成立，歌词一到就可以渲染兜底。
> - **并入新计划：** 第 0 阶段（计时）改成按 bar 记录；第 4 阶段（打包和 Opus）成为新计划的第 7 阶段。
> - **第 5、6 阶段：** 仍然可选。


## 目标

在**现有架构**下（render server、协议 v2、R3 在 Mac 端），把一个 chunk 准备过程中能并行的步骤并行起来，缩短“从上一个 chunk 提交，到这个 chunk 可以播放”的时间，让余量变大。

这份计划和 [2026-10-08 阶段图计划](2026-10-08-rap-omni-pipeline-streaming-plan.md)互相独立，可以先做：

- 这里的改动都在当前代码里，不依赖 SGLang-Omni 的阶段图改造。
- 阶段图改造之后，这里的“跨 chunk 提前写词”会自然变成“写词 stage 和 MOSS stage 同时处理不同的 chunk”，做法不同，但思路和收益一样。

依据：2026-10-08 对每一步耗时和依赖的逐项分析，数据来自：

- 10-01 H200 的端到端测量：`output/h200_e2e_20261001/`；
- Mac 本地 v2 验收，以及真实会话的事件日志：`output/rap_local_mac_v2_accept/`。

## 非目标

- 不改 MOSS 的模型和推理方式。续写、按 bar 合成在阶段图计划里做。
- 不改协议 v2 的音频交付格式。只在请求里加一个不参与请求身份的可选字段，见第 3 阶段。
- 不缩短前瞻，仍然是 2 小节。
- **不提前发请求。** 现在下一个 chunk 在当前 chunk 提交时才发请求；如果改成“上一个响应一回来就发”，余量确实会更大，但前瞻实际上变长了，听众换主题要更晚才能体现出来，和缩短前瞻的方向相反。

## 现状：一个 chunk 的关键路径

从 chunk N 提交（离它开始播放还有 1 tick），到 chunk N+1 可以播放：

| 步骤 | H200（隧道） | Mac 本地 | 依赖 |
|---|---:|---:|---|
| ① 排下一个 chunk | 0 | 0 | 上一个 chunk 提交 |
| ② eSpeak 兜底渲染，2 个 bar 串行 | 约 420 ms | 约 420 ms | 不依赖远端，但代码里远端请求要等它做完 |
| ③⑩ 网络 | 约 665 ms（当天 VPN） | 约 0 | — |
| ④ Qwen 写词（p50 / p90） | 147 / 196 ms | 920 / 1363 ms | 只依赖上一个 chunk 的**歌词文本** |
| ⑤ 选词 | 5 ms | 5 ms | 两个 bar 的候选 |
| ⑥ MOSS | 769 ms | 2111 ms | 两行完整的文本 |
| ⑦ MMS | 20 ms | 54 ms | 完整的 source |
| ⑧ 打包和落盘（含一次预演） | 61 ms | 约 29 ms | 全部结果 |
| ⑨ Opus 编码 | 60 ms | — | 打包好的 PCM |
| ⑪ Mac：解码、R3、混音 | 约 116 ms | 约 52 ms | 完整的包 |
| **合计：从提交到就绪** | **约 2.3 s** | **约 3.6 s** | |
| 到下一次提交的余量 | 约 3.0 s（估算） | **约 1.5 s（实测）** | |

关键发现：

1. **② 和远端请求是被代码顺序串起来的，两者之间没有依赖。** 每个 chunk 白白少了约 0.42 s 的远端预算。
2. **④ 只依赖上一个 chunk 的歌词文本。** 而这段文本在上一个 chunk 请求发出后约 0.2 s（H200）或约 1 s（Mac）就已经确定了，可以提前好几秒写下一个 chunk 的词。Mac 上这一步占约 0.9 s。
3. **④ 的补救轮是串行的第二轮。**
   - Mac：24 个 chunk 里有 9 个触发补救，Qwen 的 p90（1363 ms）比 p50（920 ms）多约 0.45 s。
   - H200：两次 10-01 测量里，每组 52 个 bar 中有 13 到 14 个触发补救。
4. **⑧ 每次打包都做了两遍：** 第一遍只是为了测出打包耗时、写进 manifest。
5. ⑨ 和 ⑪ 的解码、R3 都是起一个外部进程、走临时文件来做。

## 第 0 阶段：先把计时补全

现在的事件日志能推出大部分时间，但有几个点要算才能得到。先在控制器里把每一步的时间戳都打出来，后面每个阶段都用同一套指标。

- **新增事件或字段：**
  - 兜底渲染的开始和结束，按 bar 记；
  - 远端请求发出；
  - 响应到达；
  - Mac 端处理（解码、R3、混音）完成；
  - 提交。
- **服务器端：** manifest 的 diagnostics 增加 `prefetch` 小节（第 3 阶段用），以及这个请求的 Qwen 写词有没有命中预取。
- **`client_simulation.py`：**
  - 新增 `--cadence-ms 5333`：按真实节奏发请求，而不是一个接一个连续发，否则测不出预取的效果；
  - 新增 `--send-next-chunk`：模拟带上 `next_chunk` 字段。
- **指标：**
  - 从提交到远端就绪的时间；
  - 远端完成后到提交的余量；
  - 服务器各阶段的时间；
  - 预取命中率；
  - 兜底率；
  - underrun。

  分 H200 和 Mac 两种部署记录。

## 第 1 阶段：兜底渲染和远端请求并行

改动只在 Mac 的控制器（`chunk_realtime.py`）：

1. **同时开始：** `_schedule_next_locked` 同时提交两件事：远端请求和兜底渲染。远端请求不再等 `_stage_pair` 完成。
2. **两个 bar 的兜底并行渲染：** eSpeak 是 CPU 进程，两个之间互不影响。
3. **提交时的选择规则不变：** 远端在提交点之前就绪就用远端，否则用兜底。
4. **兜底没准备好的情况：** 兜底可能还没准备好，远端就已经回来了；也可能到提交点两者都没好。
   - 这时保持现在的规则：兜底没准备好就不能提交，会记录 `deadline_miss`。
   - 兜底只需要约 0.4 s，而一个周期有 5.3 s，这种情况几乎不会发生，但要有测试覆盖。
5. **deadline：** 远端请求的 deadline 仍然是提交点；预算从发出请求时开始算，比现在多出约 0.42 s。

**测试（`test_chunk_realtime.py`）：**

- 远端请求在兜底渲染完成之前就已经发出。
- 兜底先好、远端先好、两者都没好，这三种情况下的提交结果都正确。
- 停止、重置和 epoch 切换时，两个并行的任务都会被正确取消。

**验收：**

- 真实会话 24 小节，Mac 本地：
  - 从提交到发出请求的中位数，从 418 ms 降到 20 ms 以内；
  - 余量中位数增加约 0.4 s；
  - underrun 为 0；
  - 兜底率不变差。

## 第 2 阶段：一次生成 20 条，去掉补救轮

1. **新的 profile：** `RemoteCandidatePolicy.realtime_20()`，参数是 initial 20、rescue 4、max 24、min_valid 3。合格的不足 3 条时才补救；按现有数据估计，这种情况会很少。
2. **渲染预留保持不变：** H200 3000 ms，Mac 3500 ms。补救变少后，Mac 的预留以后可以重新评估，但不在这一步改。
3. **服务器端：** vLLM 的 `--max-num-seqs` 要能容纳两个 bar 各 20 条，也就是 40 条，改成 48。Mac 的 mlx_chat 合批上限也要能容纳 40 条。
4. **对比：** 同一组场景、同一个 seed，比较 `realtime_default` 和 `realtime_20`：
   - Qwen 写词的 p50 和 p90；
   - 补救比例；
   - 每个 bar 的最高分和合格候选数；
   - 被选中歌词的 WER。

**验收：**

- Qwen 写词的 p90：Mac 从 1363 ms 降到 1000 ms 以下，H200 从 196 ms 降到 170 ms 以下。
- p50 不变差，误差在 10% 以内。
- 选词质量指标不下降。

## 第 3 阶段：跨 chunk 提前写词（服务器端预取）

### 做法

1. **协议：** `RemoteRapChunkRequest` 新增可选字段 `next_chunk`，包含 `chunk_index`、`bars`（bar、主题、flow）和 `seed`。
   - 它**不参与** `request_id`，和 `remaining_budget_ms` 一样，所以缓存和幂等都不受影响。
   - Mac 的控制器知道剧本，所以能填这个字段。听众换了主题，也只是预取不命中，结果仍然正确。
2. **服务器端预取：**
   - 请求 N 选定歌词后，服务器预测请求 N+1 的写词输入：context 等于（请求 N 的 context 加上请求 N 选中的两句），取最后 4 句；bar、主题、flow 和 seed 取自 `next_chunk`；tempo 和策略沿用请求 N。
   - 然后在后台跑一次完整的写词和选词：wave、补救、配对都和正常路径完全一样。预取用固定的预算，比如 5000 ms，不受客户端 deadline 约束。
   - 结果放在内存里，键是这些写词输入的规范化哈希。每个会话只保留一份；会话结束、重置或停止时清掉，超过一定时间也会过期。
3. **使用预取：**
   - 请求 N+1 到达后，先算出它的写词输入哈希。
   - **命中：** 预取已经完成就直接用；还在跑就等它，但不超过请求自己的 deadline。
   - **不命中：** 走正常路径。不命中的原因包括：chunk N 在 Mac 上被兜底替换、换了主题、服务重启。
4. **什么时候开始预取（D3）：**
   - 服务器参数 `--lyric-prefetch {off,after_plan,after_render}`。
   - H200 用 `after_plan`：写词和 MOSS 在不同的卡上。
   - Mac 用 `after_render`：等 MOSS 和 MMS 做完再写，避免和 MOSS 抢 GPU。
   - 默认是 `off`。
5. **诊断：**
   - `stage_timings_ms.generation` 只算这个请求自己等待写词的时间。命中时接近 0。
   - 新增 `prefetch`：是否命中、预取本身的写词耗时、预取完成到被使用之间的间隔。
   - candidate ledger 原样记录预取时生成的候选。
6. **producer 指纹：** 预取不改变“相同输入得到相同分布的结果”这一点，所以指纹不变。但 manifest 里要能看出这次用的是不是预取的结果。

### 不确定的地方

- **命中率：** 取决于 chunk N 在 Mac 上被兜底替换的比例。现在是 4% 到 8%，这部分主要来自 `no_valid_candidates`，所以命中率预计在 90% 以上。
- **采样的随机性：** vLLM 采样不固定 seed，预取和正常路径选出的歌词本来就不会逐字相同，只是分布一样。
- **服务器负载：** 预取让服务器在空闲时间里多做了一次写词，但没有让总工作量增加：命中时，正常路径就不用再写了。

### 测试

- **预测的输入：** 用假生成器验证，命中时预取结果和正常路径的 ledger、选择完全一致。
- **不命中的情况：** context 不同、主题不同、seed 不同都会走正常路径，结果正确。
- **预取的生命周期：** 预取还在跑时请求就到了，会等待它；等待时间不超过请求的 deadline。预取失败或抛异常时，退回正常路径。
- **清理：** 会话重置或停止、epoch 切换时，预取被取消，内存被释放。
- **身份：** `next_chunk` 不同的两个请求，`request_id` 相同。
- **Mac 上的 `after_render`：** 预取不会和 MOSS 同时运行。

### 验收

- `client_simulation --cadence-ms 5333 --send-next-chunk`，24 个 chunk：
  - 命中率不低于 90%；
  - 命中时服务器的写词耗时不超过 10 ms；
  - Mac 本地服务器端合计时间从约 3.1 s 降到约 2.2 s；
  - H200 降低约 0.15 s。
- Mac 真实会话：余量中位数达到 2.5 s 以上，underrun 为 0，兜底率不变差。

## 第 4 阶段：打包只做一遍；Opus 编解码改成进程内

1. **打包（`rap_render_server.py`）：**
   - 去掉预演的那一遍。
   - manifest 里的 `packaging` 改成近似值：前面各步的实测时间，加上最近几次正式发布耗时的滑动平均（D4）。
   - 精确值写进 `server_timing.json` 和 `Server-Timing` 头。
   - fsync 和“先发布、后返回”的顺序不变，缓存的正确性不受影响。
2. **服务器端 Opus 编码：**
   - 用 PyAV 在进程内调用 libopus，省掉每次启动 ffmpeg 的开销，大约 39 ms。
   - ffmpeg 的实现保留，可以切回。
3. **Mac 端 Opus 解码：** 同样改成进程内。
4. **等价性：** 两种实现要先比较。同一段 PCM 编码出的包要相同，或者解码后的 PCM 逐样本相同。做不到的话，至少要满足 10-01 第 4 阶段的音质门槛，并且新实现要写进 producer 指纹。

**测试：**

- 打包只做一遍：调用次数和文件写入顺序都要有测试。
- 两种 Opus 实现在 20 段语料上做等价性比较。
- 已有的缓存和幂等测试全部通过。

**验收：** H200 上打包加 Opus 编码，从约 121 ms 降到 60 ms 以下；Mac 端解码从 59 ms 降到 20 ms 以下（H200 路线）。

## 第 5 阶段（可选）：MOSS 流式输出，vocoder 和 decode 重叠

- **SGLang 后端：** 改用 `stream=true` 加 `response_format=pcm`。vocoder 每生成 8 行就解码一段，和 decode 重叠；render server 收齐之后再拼成 source WAV。
- **注意：**
  - 流式下得到的 WAV 必须和非流式的逐字节相同，否则要单独进 producer 指纹。0.1.4 的流式路径会重复发出续写的前缀行；我们不用续写，不受影响，但要有测试。
  - Mac 的 MLX 服务先不改。
- **预计收益约 25 ms。** 只有在第 1 到 4 阶段做完之后，H200 的余量仍然是瓶颈时才做。

## 第 6 阶段（可选）：Mac 端 R3 改成进程内调用

- 用 ctypes 或 cffi 直接调用 librubberband：R3 引擎，key-frame map 等于时间映射，处理流程和参数与 `rubberband --fine --timemap` 命令行保持一致。
- **门槛：** 在 10-01 的 37 个 chunk 上，和命令行版本的输出逐字节相同。不相同就不上线，因为服务器 v1 和 Mac v2 之间“逐字节相同”的保证要保留。
- **预计收益约 20 ms。**

## 第 7 阶段：整体复测

- **H200：** 按 10-01 的测量协议，加上 `--cadence-ms`：基线和优化各跑 24 个 chunk，各一轮。
- **Mac：** client_simulation 一轮，加真实会话 24 小节。
- **记录：**
  - 关键路径上每一步的时间；
  - 余量；
  - 命中率；
  - 兜底率；
  - underrun。

  更新 profiling 报告，并在本计划末尾追加实施记录。
- **目标：**
  - H200 从提交到就绪约 1.6 s；
  - Mac 约 2.3 s，余量约 3.0 s；
  - 兜底率不变差，underrun 为 0。

## 执行顺序

```text
第 0 阶段（计时）
  → 第 1 阶段（兜底并行，只改 Mac 控制器，收益确定）
  → 第 2 阶段（一次生成 20 条，基本只改配置）
  → 第 3 阶段（预取，收益最大，改动也最大）
  → 第 4 阶段（打包、Opus）
  → 第 7 阶段（复测）
第 5、6 阶段视复测结果再定。
```

第 1、2 阶段互相独立，可以并行做。第 3 阶段要在第 2 阶段之后做，因为预取会照搬新的候选策略。

## 风险
