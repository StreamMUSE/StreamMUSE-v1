# BARS 论文笔记：按伴奏直接生成 rap 人声的 Flow Matching 模型

记录日期：2026-11-11。起因：老师对 BARS 的生成效果很满意，后面可能要学它的做法，或者把它接进我们的实时系统。

## 1. 一句话

给一段伴奏、一段歌词和 3 秒参考人声，模型一次性生成和伴奏等长的 rap 人声，再和伴奏混在一起。它不是自回归的，不预测时长，也不做音素级对齐：歌词落在哪一拍，是模型听着伴奏自己决定的。

## 2. 模型

### 2.1 输入

| 输入 | 怎么进模型 |
|---|---|
| 伴奏（beat track） | 用音频 VAE 编成潜变量，投影到低维后和人声潜变量按通道拼在一起，逐帧提供节奏 |
| 歌词 | 预训练的 ByT5-base（按字节编码）加一个一起训练的小 Transformer 适配器，通过交叉注意力注入 |
| 3 秒参考人声 | 同一个 VAE 编码，投影后接在输入序列最前面，不需要对应的文字 |
| 时间步 | 正弦嵌入，也接在序列最前面 |

- VAE 沿用 Stable Audio 2.0 的结构，用他们自己的音乐数据训练。伴奏、参考人声、目标人声共用这一个编码器。
- 用 ByT5 而不是语音预训练的文本编码器（如 SpeechT5），理由是 rap 歌词里的俚语、缩写、数字不会变成词表外的符号。

### 2.2 训练目标

- Flow Matching，带 span masking：随机选一段连续区间盖住，模型只在被盖住的区间上算损失，没盖住的部分保留真值作为上下文。
- 盖住的比例：10% 的概率盖住整段；否则盖住 70% 到 100%。
- 这个训练方式带来两个能力：局部重新生成（改几句歌词，其余不动），以及用参考人声做零样本音色控制。

### 2.3 网络结构

- 一摞 Transformer 块，每块是双向自注意力、交叉注意力、前馈网络。
- 自注意力用 RoPE，位置编号在每一段（条件 token、音频 token）开头各自归零。
- 交叉注意力只让音频 token 去查歌词，时间步和参考人声的 token 这一步先拿出去，之后再放回来。

### 2.4 A-RoPE（论文的主要贡献）

- **问题：** 伴奏的条件很强时，模型会优先对上节奏而不顾歌词，表现为跳词或重复。歌词长度和伴奏能容纳的长度差得越多越严重。
- **做法：** 交叉注意力里，音频一侧用普通 RoPE；歌词一侧的位置乘上 `S = N / L`（`N` 是音频帧数，`L` 是歌词 token 数）。相当于把歌词均匀铺在整段音频的时间轴上，让第 `i` 帧倾向于看第 `i · L / N` 个 token。
- **效果：** 注意力图从有跳变、有重复变成一条平滑的对角线。它只是一个偏向，不是硬约束，长音和停顿时可以偏离对角线。

### 2.5 规模、训练和推理

| | |
|---|---|
| 参数量 | 约 2 亿 |
| 数据 | 约 1500 小时英文 rap，男女都有；每条样本是人声片段、对应歌词、伴奏，加同一位 rapper 另一段里取的 3 秒参考 |
| 训练 | 50 万步，8 张 H100，AdamW 峰值学习率 1e-4，batch 64，EMA 0.9999 |
| 长度 | 训练样本最长 60 秒；更长的没有测过 |
| 推理 | Euler 25 步，classifier-free guidance 3.0；输出长度等于伴奏长度 |
| 速度 | 单张 RTX 4090 上 10 秒音频用 0.27 秒（实时率 0.027），包含 VAE 编解码和文本编码 |

论文没有写的：采样率、潜变量帧率、层数和隐藏维度、训练花了多久、数据来源和授权。

## 3. 速度怎么控制

没有显式的速度参数。输出长度等于伴奏长度，所以同样的歌词配更短的伴奏就 rap 得更快，配更长的就更慢。试听页的“速度控制”就是靠裁剪伴奏做的。

训练数据的语速是每秒 17.9 个字符，标准差 2.9。

## 4. 结果

**歌词准确度（Whisper large-v3 的词错误率，歌词和伴奏原本配套）**

| 配置 | WER |
|---|---:|
| 真人录音 | 5.1% |
| ByT5 + 适配器 + A-RoPE（完整模型） | 5.1% |
| 去掉 A-RoPE | 6.0% |
| 去掉适配器 | 9.7% |
| 两个都去掉 | 37.7% |
| SpeechT5 + 适配器 + A-RoPE | 5.6% |

**歌词和伴奏随机错配时（语速按训练分布分成 5 档）**

| 语速 | 完整模型 WER | 去掉 A-RoPE |
|---|---:|---:|
| 均值 − 2σ（最慢，约每秒 12 个字符） | 20.5% | 33.6% |
| 均值 − 1σ | 14.2% | 25.5% |
| 均值 | 12.3% | 22.0% |
| 均值 + 1σ | 13.8% | 24.4% |
| 均值 + 2σ（最快，约每秒 24 个字符） | 15.4% | 26.9% |

- 慢的时候错误主要是多出来的词，快的时候主要是漏词。
- 错配时的 WER 比配套时高一倍以上，论文的解释是配套的歌词本来就是照着伴奏写的。

**音色和音质**

- 和参考人声的相似度（WavLM）：配套时 0.80，和真人录音一样；错配时 0.75。
- DNSMOS：3.46 到 3.49，略高于真人录音的 3.35。

**主观听评（40 人，5 分制，错配条件下且只挑了 WER 低于 5% 的样本）**

| | 节奏感 | 音色相似 | 音质 |
|---|---:|---:|---:|
| 真人录音 | 3.81 | 3.95 | 3.73 |
| 完整模型 | 3.51 | 3.82 | 3.35 |
| 去掉 A-RoPE | 3.34 | 3.98 | 3.46 |

**论文自己说的局限：** 只在英文上评估过；多语言只有试听页上的初步样例。另外，局部重新生成这个能力论文只描述了做法，没有给出评估数字。

## 5. 和我们现在的系统对比（我的分析）

| | 我们（协议 v3，v1.1） | BARS |
|---|---|---|
| 歌词从哪来 | Qwen 实时写 | 外部给定，模型不写词 |
| 人声 | MOSS-TTS 说出来 | 直接生成 rap 人声 |
| 节奏怎么来 | flow 模板规定每个音节的位置，MMS 找实际位置，R3 拉伸过去 | 模型听伴奏自己安排，没有模板，也没有对齐和拉伸 |
| 伴奏 | 本地合成的鼓，人声不知道伴奏是什么 | 伴奏是模型的输入，人声跟着伴奏的风格走 |
| 生成方式 | 自回归，逐 bar，续写上一个 bar | 一次生成整段，长度固定 |
| 音色 | 参考音频加续写，回合之间会变（已知问题） | 3 秒参考，相似度 0.80 |
| 每个 bar 的耗时 | MOSS 约 0.44 s，加对齐和拉伸约 0.1 s（H200） | 10 秒音频 0.27 s（RTX 4090） |
| 能不能拿到 | 全部开源组件 | 代码和权重都没公开 |

BARS 省掉的正好是我们最别扭的那一段：TTS 说话、强制对齐、再拉伸成 rap。我们声音听起来像“被拉伸的朗读”，它听起来像 rap，差别主要来自这里。

反过来，它没有我们的两样东西：

- **写词。** 它只负责把给定的歌词 rap 出来，实时写词还是要我们的 Qwen。
- **显式的节奏控制。** 它不能指定“第 3 个音节落在第 6 个 tick”。我们的 flow 模板、cyclic 模式里“用户敲节奏、模型照着回应”，在它的接口里没有对应的输入。

## 6. 如果要把它做成实时的（我的分析）

**它本身不能流式输出。** 自注意力是双向的，25 步积分每一步都要处理整段，输出长度一开始就由伴奏定死。所以“流式”只能是分段生成：每次生成一小段，接在已经播出的后面。

**有利的地方**

- **够快。** 实时率 0.027，生成一两个 bar 只要零点几秒，比我们现在每个 bar 的合成还快。分段生成在算力上没有问题。
- **接续有现成的机制。** span masking 就是“保留一部分已有音频、生成其余部分”。把已经播出的音频当作没盖住的上下文，生成后面的部分，和训练时做的事情是同一类。
- **改主题有现成的机制。** 还没播的部分换上新歌词重新生成，就是论文说的局部重新生成。
- **音色稳定。** 每一段都用同一段 3 秒参考，不依赖上一段的续写。

**要解决的问题**

- **上下文的比例。** 训练时盖住的比例是 70% 到 100%，也就是保留的上下文最多 30%。滑动窗口要照这个比例设计；上下文更长或新生成的部分更短时效果如何，论文没有数据。
- **歌词要铺满整个窗口。** A-RoPE 假设歌词大致均匀地铺在整段音频上。分段时，窗口里的歌词必须包含上下文那部分已经唱过的词，而且每段的歌词量要和时长相称。
- **语速范围。** 我们 60 BPM、每个 bar 9 个音节，粗算每秒只有 8 到 10 个字符，比它训练分布的均值低了约 3 个标准差；90 BPM 时大约低 1 个标准差。慢速下它的错误率明显升高（−2σ 时 20.5%）。要么写更密的词，要么用更快的 BPM。这是粗算，没有量过我们真实歌词的字符数。
- **界面上的音节网格。** 它不产生每个音节的时间。要继续显示歌词跟随，得在生成之后跑一次对齐，只用于显示。
- **用户敲的节奏怎么给。** 一个可以试的想法是把敲击渲染成打击乐放进伴奏里，让模型跟着。没有任何证据说明这样有效。
- **超过 60 秒没测过。** 分段生成每个窗口都短于 60 秒，可以绕开；但长时间滚动下去会不会漂，是未知的。

## 7. 拿不到权重时，自己做一个的代价（我的分析）

| 部分 | 有没有现成的 |
|---|---|
| 文本编码器 ByT5-base | 公开 |
| 模型结构和训练方法 | 论文写得比较完整，但层数、维度没给 |
| 音频 VAE | 他们用自己的数据训的；公开的 Stable Audio Open 带一个同类 VAE，能不能直接用要核实 |
| 数据：1500 小时带歌词的 rap 人声加对应伴奏 | **没有公开的。** 需要自己收集、做人声分离、拿到歌词、按 rapper 分组。这是最大的障碍，也有版权问题 |
| 算力 | 8 张 H100 跑 50 万步；论文没写用了多久 |

另一条路是直接联系作者要权重或接口。BandLab 是商业公司，论文里的 VAE 和数据都是自有的，能不能给不确定。同类的前作 Freestyler（AAAI 2025，自回归）也没有公开权重。

## 8. 下一步可以做的

1. 听完试听页，记下它相对我们明显好在哪、有没有明显的问题（比如快速段的漏词）。
2. 问作者：权重或推理接口能不能给研究用；采样率、潜变量帧率、层数这些论文没写的参数。
3. 量一下我们真实歌词的每秒字符数，确认第 6 节里语速范围的粗算。
4. 在决定之前不动现在的系统。[合并计划](../plans/2026-11-11-rap-inference-optimization-and-carryover-plan.md)的非目标里写着“不换 TTS 模型”，要走这条路需要先改那一条。
