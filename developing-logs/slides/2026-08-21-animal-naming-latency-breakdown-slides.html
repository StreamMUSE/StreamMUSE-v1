为什么不是 175 ms？

说完后还要等待约 313 ms trailing silence，然后执行 resample、关闭 PortAudio stream，再运行约 175 ms ASR。
313+约 104+175≈592 ms
Parser、terminal render 与 game validation 加起来远低于 1 ms，所以 last_voice_to_decision 几乎等于 last_voice_to_asr_text。
系统可控延迟应优先看 last_voice_to_decision，而不是包含 Human reaction 的整轮时间

为什么 TTS prewarm 为零？

Animal Naming 有 91 个可能输出，V1 禁止启动时一次性合成整个 whitelist，因此 prewarm_entry_count=0。
这也意味着本局十个不同动物全部走 cold on-demand synthesis，单局内 memory cache 没有收益。
Markdown renderer 当前只输出 turn metrics；startup 数值保存在 breakdown_summary.json 的 startup 数组。
启动成本应该与 steady-state turn latency 分开报告

What the trace says

当前瓶颈排序

01
TTS synthesis

p50 901 ms，p95 1297 ms；比 LLM inference 更慢，是最大的系统计算延迟。

02
Human reaction + speaking

等待开口 p50 895 ms，发言 p50 633 ms；它们影响 deadline 体验，但不应被误认为系统 inference。

03
VAD endpoint + stream cleanup

尾部静音约 313 ms，加上关闭与整理，使说完到 ASR 文本约 592 ms。

04
LLM HTTP

p50 353 ms，p95 679 ms；本地 JSON 和 parsing overhead 可以忽略。

05
STT inference

pipeline p50 175 ms，p95 230 ms；当前不是延迟大头，但准确率仍需独立 qualification。

延迟快不等于识别准确；这两类指标必须分开报告

Metric semantics

Human E2E 需要拆成两种口径

体验口径

turn.response_source_ms

p502113 ms
p952940 ms

包括开麦、Human reaction、说话、VAD、STT。

系统口径

human.last_voice_to_decision_ms

p50593 ms
p95655 ms

排除 Human reaction，更适合衡量系统优化。

如果 acceptance criterion 只写“Human end-to-end p95 ≤ 2500 ms”，这局会得到 2940 ms 并判 fail，但主要原因是用户等待开口。正式报告应同时给出体验口径与系统口径。
deadline 体验与系统性能有关，但不能用一个数字混在一起解释
