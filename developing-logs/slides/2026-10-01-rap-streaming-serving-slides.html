整体流程

“实时”指准备速度追得上播放速度

Mac 播放第 N 段时，H200 在准备第 N+1 段。每段是两小节人声，必须在下一段开始前准备好。

节拍单位

90 BPM 时一小节 2.667 s；一个 chunk 是两小节，5.333 s，输出 24 kHz 下正好 128000 帧。

截止时间

远端请求最多等 5.0 s，而且要在下一段开始前 1 tick 冻结选择，所以服务器拿不到完整的 5.333 s。

兜底

远端迟到或失败，就用 Mac 上提前备好的 eSpeak 人声，音乐时钟不等人。

Omni serving

Omni 模型天然是一条多阶段流水线

以 Qwen2.5-Omni 为例：Thinker 负责理解和生成文本，Talker 把 Thinker 的隐状态变成语音 token，再由 sliding-window DiT 流式解码成波形。

  • 各阶段的计算方式差别很大：编码器一次前向，Thinker 和 Talker 逐 token 自回归，解码器按窗口做 DiT。
  • 塞进一个引擎统一调度，batch 大小、显存和 GPU 分配很难同时照顾好。

来源：Qwen2.5-Omni Technical Report，arXiv 2503.20215

5 / 21
Omni serving

vLLM-Omni / SGLang-Omni：按阶段图来 serve

  • 阶段图：每个组件是一个 stage，有自己的引擎、batching 和 GPU 分配；用 YAML 配路由，支持提前结束、回环和一对多输出。
  • 分离部署：瓶颈阶段可以多开实例，思路是 LLM 里 prefill / decode 分离的推广。
  • 阶段间流式：下游拿到一个 chunk 就开工，主要压低首包延迟。vLLM-Omni 论文报告 JCT 最多降低 91.4%。论文数据

Streaming 的三种含义

Output：输入一次给齐，输出边生成边返回。

Sequential：输入流式进入，读完再生成。

Concurrent：边收边出，全双工。

这些 serving 框架做的是系统层面的 output streaming。“边听边想边说”属于模型层面的 concurrent streaming。分类来自综述 arXiv 2603.04592。

来源：vLLM-Omni，arXiv 2602.02204；SGLang-Omni 设计 RFC，sgl-project/sglang#16546

MOSS

MOSS-TTS：每一步同时出 33 个 token

一个 8B 的自回归语言模型。每一步输入一行 33 个 token，输出下一行：1 个文本控制 token 加 32 个音频码本 token。

音频 codec

MOSS-Audio-Tokenizer：24 kHz 波形对应每秒 12.5 帧，每帧 32 个码本。

Prompt

参考音频 codes、风格指令、目标 token 数、歌词文本。

长度控制

两小节 5.33 s 对应目标 67 个 token，实际输出 68 帧，也就是 5.44 s。

MOSS

Delay pattern：68 帧为什么要跑约 101 步

总步数 = 帧数 + 码本数 − 1。每一帧都要等最后一个码本生成完才完整。

68 → 101
MOSS 实际：32 个码本、68 帧，trace 中是 101 次 decode实测
≈240ms
约 33 步不产生新帧的时间。这是模型结构决定的，serving 层去不掉。
8 / 21
MOSS on SGLang-Omni

MOSS 在 SGLang-Omni 里分成三个 stage

收益主要在 tts_engine

FA3、decode 和采样都用 CUDA graph，33 个输出头合并成一次矩阵乘。

三个 stage 放在一起

同一进程、同一张 GPU，stage 之间直接传进程内对象，hop 只要约 0.1 ms。

没用到的能力

分离部署和跨 stage 流式都还没用上：我们一次只跑一个请求，下游也需要完整音频。

新后端

新后端：MOSS 拆成独立服务，其余环节不变

  • 独立服务：版本固定为 SGLang-Omni 0.1.4、SGLang 0.5.18，启动前用 preflight 检查环境。
  • HTTP adapter：同一个 deadline 贯穿全流程，请求可取消，下载有上限，收到后校验完整 WAV。
  • 配置按单请求低延迟调：一次只跑一个请求，CUDA graph batch 为 1，打开参考音频编码缓存。
  • 仍用 stream=false：MMS 和 R3 需要完整的 source 才能对齐和拉伸。
  • 缓存按 producer 指纹隔离：换后端不会误用旧 WAV；健康检查要求真实 WAV 预热通过。
  • 默认仍是旧后端，新后端要显式开启。

结果

MOSS 内部：90% 的时间花在 decode

  • 主干受显存带宽限制：每步读约 13.9 GB 权重，GEMM 约达到 H200 峰值带宽的 66%。
  • 每步约 1.3 ms GPU 在等 CPU：采样后处理、逐个查 33 张 embedding 表、调度记账，都在两次前向之间串行执行。
  • 文本头有浪费：每步算完整的 15.5 万词表，实际只用其中 2 列控制 token。
  • delay 尾部约 240 ms 是模型结构决定的。

为什么

Mac 路线：比 H200 慢，但够用，而且稳定

和 H200 比

  • MOSS 2.11 s，是 H200（0.77 s）的 2.7 倍，占 Mac 准备时间的 64%。
  • Qwen 0.92 s，H200 是 0.15 s。不共享 prefill 时，两个 bar 32 条要 6.1 s。
  • 但没有网络这一段，结果不受 VPN 影响；也不用 Opus，人声直接走 PCM。
  • WER 不比 H200 差。

还能做的

  • MOSS 4-bit：约快 0.7 s，要先通过音质门槛（WER 和盲听）。
  • MLX 生成支持中途取消：迟到的请求不用再占着 GPU。
  • 渲染预留：现在是 3500 ms。如果想让 fallback 降到 0，可以再调大，代价是基本不会再做补充生成。
  • 多会话：一台 Mac 同时只服务一个 demo，还没测并发。

小结与讨论

这段时间做了什么

  • MOSS 换到 SGLang-Omni：单段合成快 3.25 倍。
  • 按 profiling 落地了六项改动：服务器准备一个 chunk 实测从 1.37 s 降到 1.09 s，MOSS 输出逐字节不变。
  • R3 移到 Mac，修好了 gentle_sparse chunk 被全部拒收的问题。
  • 整条流程能在 Mac Studio 本地跑：端到端 p50 3.3 s，24 / 24 被接受，underrun 为 0。

想讨论的问题

  • demo 用 H200 还是 Mac 本地？H200 快，但受 VPN 影响；Mac 慢一些，但没有网络开销。
  • 要不要做真正的流式：MOSS 边生成，MMS 和 R3 边对齐拉伸？
  • MOSS 补丁要不要提给上游 SGLang-Omni？
  • “边听边想边说”的 concurrent streaming 和 serving 优化是两条线，先做哪条？
